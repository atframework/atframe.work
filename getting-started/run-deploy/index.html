运行与部署

本地快速运行​

构建产物在 <BUILD_DIR>/publish/。先在 install/cloud-native/values/personal/ 填写本地覆盖值并构建，或临时修改 publish 中的 values。 至少确认 etcd、Redis 地址、实例布局和 Excel 资源路径。 本地生成脚本依次加载 default、dev、personal，并设置 global.world_id=1； 需要其他 world id 时调整调用参数。

Linux / macOS​

cd <BUILD_DIR>/publish/tools/script
bash start_local_test_env.sh
bash generate_config.sh
cd ../..
bash start_all.sh

Windows​

Set-Location <BUILD_DIR>/publish/tools/script
pwsh -NoLogo -NoProfile -File start_local_test_env.ps1
pwsh -NoLogo -NoProfile -File generate_config.ps1
Set-Location ../..
pwsh -NoLogo -NoProfile -File start_all.ps1

已有外部依赖时可跳过统一启动脚本，但 values 必须使用对应地址；只需要其中部分本地依赖时，可直接调用 tools/script/etcd/、redis/ 或 openobserve/ 下的管理脚本。三个组件的默认工作目录为 tools/script/var/local-test-env/ 下的 etcd、redis 和 openobserve 子目录，以脚本所在目录为基准， 不受调用时当前目录影响；可用 --work-dir 或 -WorkDir 覆盖。 generate_config 先用 Helm 更新打包的 chart 依赖，再调用发布的 atdtool，生成每实例 YAML 和启动脚本，以及 publish 根目录的 start_all、stop_all、kill_all。检查服务日志和 etcd 注册后，再验证业务请求。 依赖更新失败时停止生成。修改 libapp 源模板后，必须同步刷新各服务 charts/libapp-*.tgz， 否则渲染仍会使用旧脚本。直接调用 atdtool 前，先运行 tools/script/update_dependency.sh/.ps1。

本地 OpenObserve​

统一启动脚本使用 Docker、Podman 或 nerdctl 启动 OpenObserve OSS 单节点容器，端口只绑定 127.0.0.1。 首次启动自动创建 atsf4g 组织，后续启动复用已有数据与凭据。打开 http://127.0.0.1:5080， 使用账号 admin@owent.net 和以下文件中的密码登录：

tools/script/var/local-test-env/openobserve/openobserve-root-password.txt

密码由密码学安全随机数生成，POSIX 权限设为 0600。同一目录下的 values/modules/telemetry.yaml 也包含凭据，不要提交或分发。generate_config 检测到该 values 目录后会在 personal 之后加载， 因此先启动依赖再生成配置即可让 otelcol 使用相同账号、密码、组织和端口。同一 values 还配置 HPA 使用的 Prometheus HTTP API 地址与凭据，HPA 通过 OpenObserve 的 /prometheus/api/v1/query 拉取指标。

数据位于 tools/script/var/local-test-env/openobserve/data，通过独立 bind mount 持久化。stop_local_test_env 只停止并移除容器，不删除数据或密码；显式执行 tools/script/openobserve/openobserve.sh cleanup （PowerShell 使用 -Command cleanup）才会删除这些文件和本地镜像。

默认保留 14 天，容器限制为 2 CPU、3GB 内存。按每天存储不超过 5GB 估算，有效数据约为 70GB； WAL、索引、查询缓存和临时文件还会占用额外空间，建议至少准备 100GB 可用磁盘。保留策略按时间清理， 不是 5GB/天的硬配额。Shell 管理脚本使用 --retention-days、--memory、--cpus、--http-port、 --organization 等参数，PowerShell 对应 -RetentionDays、-Memory、-Cpus、-HttpPort、-Organization； 在生成配置前完成这些调整。

按实例启动与重载​

生成产物按 <server>/cfg/*_<bus_id>.yaml 和 <server>/bin/start_<bus_id>.sh/.ps1 布局存放。可只启动所需服务实例； 使用数据层的业务服务需配套依赖与组件实例。

热更新使用实例的 reload_<bus_id>.sh/.ps1，停止使用 stop_<bus_id>.sh/.ps1。 整体停止使用 publish 根目录的 stop_all.sh/.ps1；临时依赖由 tools/script/stop_local_test_env.sh/.ps1 停止。 修改配置的具体步骤见服务端配置。

进程托管​

Linux shell 脚本通过 tools/script/service-manager.sh 选择托管方式。默认 auto 依次检查 可连接的 systemd 用户管理器、PATH 中的 supervisord 和 supervisorctl，最后使用普通后台进程。 安装了 systemctl 但没有用户会话总线时，不会选用 systemd。显式指定的后端不可用时，启动报错。

bash start_all.sh -m auto
bash start_all.sh -m systemd
bash start_all.sh -m supervisord
bash start_all.sh -m none

# 单实例及依赖服务也读取此环境变量。
export ATF_SERVICE_MANAGER=supervisord
bash tools/script/etcd/setup-etcd.sh start --service-manager supervisord
bash tools/script/redis/redis.sh start --service-manager systemd --container-engine podman

运行中的实例保留最初的命令、参数、部署环境变量和后端；改变它们需要先停止再启动。每个实例在 bin/<PID 文件名>.service/ 记录控制器路径、实例名和启动参数，etcd/Redis 则使用各自工作目录的 service/。stop、kill 和 cleanup 使用这份记录，不重新探测后端，也不读取新的后端选择。 控制器不可用时保留状态并报错，恢复控制器后重试停止。迁移部署目录前先停止服务，运行中不要删除状态目录。 若上次 stop 未完成，但业务进程已退出且托管器已停止该实例，下一次 start 会先完成收尾，再按新参数启动。 仍在运行、等待崩溃重启或无法确认控制器状态时，不会覆盖原记录。已卸载且确认停止的 unit 也可正常完成 stop。 没有托管记录的旧部署仍使用原有 PID 停止方式。

可单独重复执行实例的 start/stop 脚本，无需先运行 start_all/stop_all。状态目录中的 lifecycle.record 和备份 使用 SHA-256 校验并原子替换，保存启动后端、实例名称和运行/停止意图。字段丢失或损坏、误留 stopped、误删 enabled 时从有效记录恢复；真实 stop 失败留下的停止意图仍要求先完成 stop，不会被 start 当成损坏忽略。 进程记录同时保存 PID 和启动时间，恢复前校验真实进程；应用启动确认完成后，才允许修复它的 PID 文件。 停止完成记录绑定本次进程，空标记或上一次进程的标记不会跳过业务停止命令。两份生命周期记录都损坏、记录属于 其他目录或无法确认进程身份时，脚本保留现场并报错；恢复记录或控制器后重试，不猜测后端或终止其他进程。

普通进程根据 tools/script/common/atsf4g@.service 在实例状态目录生成 unit，与 run.sh 放在一起； ~/.config/systemd/user/ 仅保存指向该 unit 的注册和启用链接，不再创建用户状态目录中的实例索引。 unit 通过 %Y 定位自身在发布包中的实际目录。systemd、Quadlet 和 supervisord 的实例标识由完整服务名和 发布根目录绝对路径的 SHA-256 前 16 位组成。后缀只取决于部署目录，不包含启动参数、执行目录、状态目录或包版本。 保留部署入口的逻辑路径，不将软链接解析成版本目录；通过同一个部署入口更新包后名称保持稳定，切换入口前应先停止旧实例。 同一部署目录中的完整服务名必须唯一，不同部署目录可以复用服务名。已有生命周期仍按记录的旧名称停止，下次启动采用新规则。 参数按原始 argv 保存并执行，服务在前台运行，systemd 跟踪实际服务进程。 生成脚本的内部前台模式参数为 --atapp-foreground。 启动时还会记录同实例生成的 stop 脚本。正常 stop 先撤销自动启动意图，调用该脚本执行应用停止命令， 并等待业务进程退出，再由托管器完成收尾；--upgrade 等停止参数按原始 argv 透传。 停止命令失败时返回失败并保留进程，修复原因后可重试 stop，或显式执行 kill。 kill 跳过业务停止命令并强制终止进程。 systemd 的 ExecStop 使用同一回调；supervisord 通过前台适配脚本接收停止请求， 不会将停止信号直接发给业务进程。每次进程运行期间，成功的停止命令仅执行一次，崩溃重启后重新计数。 直接通过 systemctl/supervisorctl 停止时也调用该回调，超时后的终止行为遵循托管器配置。 start 在同一用户共用的互斥锁内注册 unit，执行 enable --no-reload、daemon-reload，再 start。 并行启动其他实例时也遵循这个顺序；未变化的注册链接不会重建。stop/kill 先移除启动意图并 disable，再通过 systemctl 停止。 原生 unit 的 disable 还会删除注册链接。停止活跃实例时，脚本立即恢复仅用于定位该 unit 的注册， 直到业务停止命令和 systemctl stop 完成后再注销，避免进程退出后 unit 被回收导致 Unit not loaded。 这不会恢复 WantedBy 自启动链接；丢失的包内 unit 文件可从随包模板重建。 Restart=on-failure 负责崩溃拉起，enable/disable 负责用户管理器启动时的自动启动。 stop/kill 确认停止后会清除该 unit 的 failed 记录。旧测试删除配置后若仍显示 not-found/failed， 可对已确认停止的具体 unit 执行 systemctl --user reset-failed <unit>；这不会删除 journal 日志。 注销后继续运行或开机启动还需要运维按需配置 user lingering；脚本不会修改该系统设置。

supervisord 使用独立的用户级 daemon、Unix socket 和程序配置，默认目录为 <发布包>/var/service-manager/supervisor，可在启动前通过 ATF_SUPERVISOR_DIR 指定绝对路径 （不包含换行、反斜杠或分号）。该目录必须由当前用户专用。 本地构建的 tools 即使链接到源码树，默认配置仍写入发布目录。路径超过 Unix socket 长度限制时， 仅将控制 socket 放入用户运行时目录，配置、日志和 PID 文件继续保存在发布目录。 停止时移除对应程序配置并更新 daemon， 避免它再次启动时重新拉起已停实例。后台运行的服务使用 autorestart=unexpected；退出码 0 不触发重启。 普通进程模式没有崩溃重启。日志分别在 systemd journal、supervisord 目录和实例状态目录的 output.log 中。

已有容器镜像​

宿主机托管已有镜像，无需把 supervisord 加入业务镜像。容器内的主进程应在前台运行。 下面的参数在镜像名后通过第二个 -- 传给容器命令；省略该部分时沿用镜像的 ENTRYPOINT/CMD。

export ATF_SERVICE_MANAGER=supervisord
bash tools/script/service-manager.sh start "$PWD/runtime/game-1" game-1 "$PWD" \
  --container docker registry.example/game:version -- \
  --publish 127.0.0.1:7001:7001 --volume "$PWD/config:/app/config:ro"
bash tools/script/service-manager.sh stop "$PWD/runtime/game-1"

# 可选：覆盖镜像的 CMD。
bash tools/script/service-manager.sh start "$PWD/runtime/redis-1" redis-1 "$PWD" \
  --container podman docker.io/library/redis:7.2.16 -- \
  --publish 127.0.0.1:16379:6379 -- redis-server --appendonly yes
bash tools/script/service-manager.sh kill "$PWD/runtime/redis-1"

容器名、detach、restart、rm、cidfile 和 sdnotify 等生命周期参数由控制器管理，调用方不要覆盖。 Docker/supervisord 使用前台容器客户端，stop/kill 还会通过记录的引擎停止实际容器并确认退出。 绑定目录、命名卷和镜像不会随 stop/kill 删除；容器临时层和匿名卷不用于保存持久数据。 Redis 的显式 cleanup 仍遵循其原有镜像清理行为。

Podman + systemd 使用 rootless Quadlet：每实例的 .container 和启用 drop-in 都保存在实例状态目录， ~/.config/containers/systemd/ 只保存文件及 drop-in 目录的链接， 由 Podman generator 生成 unit；配置目录遵循 XDG_CONFIG_HOME。常用的 publish、volume、env、network 参数转换成 Quadlet 字段，其他引擎选项通过 PodmanArgs 传递，需要与 Quadlet 的生命周期设置兼容。 Quadlet 要求支持该功能的 Podman 和 cgroup v2。 WSL 等没有激活系统 network-online.target 的环境，若镜像已缓存且服务只需本地网络，启动前设置 ATF_QUADLET_WAIT_NETWORK=0 可关闭 Quadlet 的网络就绪等待；默认保留该等待。 生成的 unit 不能直接 systemctl enable/disable，因此 start 安装带 WantedBy=default.target 的 [Install] drop-in，stop/kill 移除它并 daemon-reload；进程启停仍通过 systemctl --user。 停止成功后移除安装的 Quadlet 链接，实例状态保留供下次启动使用。

实现依据：systemd service、 Supervisor 配置、 Podman Quadlet。

旧版 atsf4g 镜像的 /entrypoint.sh start 会后台启动业务进程、前台运行配置 watcher。 使用这些镜像时，将 tools/script/container-entrypoint.sh 只读挂载为 /atf-entrypoint.sh， 设置 --entrypoint /bin/bash，容器命令使用 -- /atf-entrypoint.sh start，并保留原来的环境变量和配置挂载。 该兼容入口复用镜像内的配置初始化、reload 和 stop，通过 health_check 发现业务进程退出并让容器失败退出， 使外部托管器能够重启容器。启动等待默认 180 秒，可通过容器环境变量 ATF_CONTAINER_START_TIMEOUT 调整。 此方式不需要重打镜像；仅监控前台容器客户端无法发现旧入口掩盖的业务进程退出。

打包与清理运行状态​

pack_publish.sh 的主包、debug 包和 otel 包都排除实例状态目录、PID/CID、启动失败标记、控制 socket、 私有 Supervisor 配置及清理备份。OpenObserve 的本地密码、生成 values 和数据目录也整体排除。 etcd/Redis/OpenObserve 在发布目录内部自定义的工作目录会识别其托管状态；配置和数据目录保留。 打包只读取运行状态，不会停止服务或清除源目录中的记录。重新生成后的包可在另一部署目录初始化自己的状态。

对于已经复制了运行状态的旧包，以部署用户在 Linux 上执行：

# 默认只列出待清理路径。
bash tools/script/reset-service-state.sh
# 备份并清除当前发布目录的失效或复制状态。
bash tools/script/reset-service-state.sh --force
# 从其他目录操作时显式指定发布根目录。
bash /path/to/publish/tools/script/reset-service-state.sh -d /path/to/publish --force

脚本不依赖生命周期记录有效，也不会根据复制来的控制器路径执行命令。发现活进程、等待中的 systemd 作业或运行容器时， 会拒绝清理并要求先正常 stop。确认私有 Supervisor 没有活动程序后，才关闭它并移走配置。 清理仅移除指向当前发布目录的实例注册链接，并在完成后刷新 systemd；其他部署的链接保留。 备份位于 var/service-manager/reset-backups/<时间戳>-<PID>/；配置、二进制、OpenObserve 密码和其他依赖数据不移动。 目录外的依赖工作目录或 ATF_SUPERVISOR_DIR 不会清理，应单独处理对应部署的状态。

部署形态​

形态输入与输出
Kubernetesinstall/cloud-native/charts/ 与 values，生成工作负载、网络、存储和日志配置
Dockerinstall/cloud-native/images/server/ 的 Dockerfile 与 entrypoint
裸机/本地non_cloud_native/deploy.yaml 的进程布局与 sh/ps1 实例脚本

日常调整只改 values。新增实例填写 proc_desc 的 chart 名、实例数、起始实例号和启动分组。 服务侧 HPA 配置随实例生成；Kubernetes HPA 和指标适配器需要另行配置，见 HPA 接入。

定制与详细设计​

需要自行调用渲染工具时，构建后的 atdtool 位于 <BUILD_DIR>/publish/tools/atdtool/；Windows 使用 atdtool.exe。 传入逗号分隔的 values 目录以沿用本地生成脚本的调用方式：

atdtool template install/cloud-native/charts -o <OUTPUT_DIR> \
  --values install/cloud-native/values/default,install/cloud-native/values/dev \
  --set global.world_id=1

实例配置的生成与部署模式由 chart 控制；原始模板和共享片段位于 install/cloud-native/charts/libapp/。 可观测性接入见遥测。
