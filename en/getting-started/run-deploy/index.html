Run and Deploy

Run Locally​

Build outputs live in <BUILD_DIR>/publish/. Set local overrides in install/cloud-native/values/personal/ and build, or temporarily edit published values. Check etcd/Redis addresses, instance layout, and Excel resource paths. Local generation loads default, dev, and personal in order and sets global.world_id=1; adjust the invocation for another world id.

Linux / macOS​

cd <BUILD_DIR>/publish/tools/script
bash start_local_test_env.sh
bash generate_config.sh
cd ../..
bash start_all.sh

Windows​

Set-Location <BUILD_DIR>/publish/tools/script
pwsh -NoLogo -NoProfile -File start_local_test_env.ps1
pwsh -NoLogo -NoProfile -File generate_config.ps1
Set-Location ../..
pwsh -NoLogo -NoProfile -File start_all.ps1

When dependencies are already available externally, omit the combined startup script and point values to those addresses. To start only selected local dependencies, invoke the management scripts under tools/script/etcd/, redis/, or openobserve/ directly. Their default work directories are the etcd, redis, and openobserve subdirectories under tools/script/var/local-test-env/. These paths follow the script location rather than the caller's current directory; override them with --work-dir or -WorkDir. generate_config first refreshes packaged chart dependencies with Helm, then invokes the published atdtool, renders instance YAML/startup scripts, and generates start_all, stop_all, and kill_all at the publish root. Dependency update failures stop generation. After editing libapp source templates, refresh each service's charts/libapp-*.tgz; otherwise rendering still uses the old scripts. Before invoking atdtool directly, run tools/script/update_dependency.sh/.ps1. Check logs and etcd registration before testing business requests.

Local OpenObserve​

The combined startup script runs a single-node OpenObserve OSS container through Docker, Podman, or nerdctl, with ports bound only to 127.0.0.1. The first start creates the atsf4g organization; later starts reuse existing data and credentials. Open http://127.0.0.1:5080 and log in as admin@owent.net with the password from:

tools/script/var/local-test-env/openobserve/openobserve-root-password.txt

The password is generated with a cryptographically secure random source and the POSIX mode is 0600. values/modules/telemetry.yaml in the same runtime directory also contains credentials; do not commit or distribute it. When generate_config finds this values directory, it loads it after personal, so starting dependencies before rendering gives otelcol the same account, password, organization, and port. The values also configure the Prometheus HTTP API address and credential used by HPA, which queries metrics through OpenObserve's /prometheus/api/v1/query.

Data lives in tools/script/var/local-test-env/openobserve/data on a separate bind mount. stop_local_test_env stops and removes the container but retains data and the password. Only an explicit tools/script/openobserve/openobserve.sh cleanup (or -Command cleanup in PowerShell) removes these files and the local image.

The default retention is 14 days, with container limits of 2 CPUs and 3GB memory. At up to 5GB stored per day, retained data totals about 70GB. WAL, indexes, query caches, and temporary files need additional space, so provide at least 100GB of free disk. Retention is time-based, not a hard 5GB/day quota. Shell management scripts accept --retention-days, --memory, --cpus, --http-port, and --organization; PowerShell uses -RetentionDays, -Memory, -Cpus, -HttpPort, and -Organization. Adjust these options before generating configuration.

Start and Reload Individual Instances​

Generated files use <server>/cfg/*_<bus_id>.yaml and <server>/bin/start_<bus_id>.sh/.ps1. Start only the instances you need; business services using the data layer require their dependencies and component instances.

Use the instance's reload_<bus_id>.sh/.ps1 for reload and stop_<bus_id>.sh/.ps1 for stopping. Use the publish root's stop_all.sh/.ps1 to stop the deployment and tools/script/stop_local_test_env.sh/.ps1 to stop temporary dependencies. See server configuration for configuration changes.

Process Supervision​

Linux shell scripts select a backend through tools/script/service-manager.sh. The default auto checks for a reachable systemd user manager, then supervisord and supervisorctl on PATH, then ordinary background processes. Having systemctl installed without a usable user bus is insufficient. An explicitly requested but unavailable backend fails.

bash start_all.sh -m auto
bash start_all.sh -m systemd
bash start_all.sh -m supervisord
bash start_all.sh -m none

# Individual instances and dependency services also read this variable.
export ATF_SERVICE_MANAGER=supervisord
bash tools/script/etcd/setup-etcd.sh start --service-manager supervisord
bash tools/script/redis/redis.sh start --service-manager systemd --container-engine podman

A running instance retains its original command, arguments, deployment environment variables and backend; stop it before changing them. Each instance records its controller path, identity and startup arguments under bin/<PID filename>.service/. Etcd/Redis use service/ in their working directories. Stop, kill and cleanup use this record without probing again or applying a new backend choice. If the controller is unavailable, state is retained and the operation fails; restore it and retry. Stop services before moving a deployment directory, and retain state while they run. If a previous stop was incomplete but both the business process and its manager have stopped, the next start finishes cleanup and starts with the new arguments. Running instances, pending crash restarts and unavailable controllers retain their records. Stop also completes for an unloaded unit once shutdown is confirmed. Older deployments without a manager record retain their PID-based stop path.

Instance start/stop scripts support repeated standalone execution without start_all/stop_all. lifecycle.record and its backup are atomically replaced and checked with SHA-256. They preserve the backend, identity and running/stop intent, allowing missing or damaged fields, stale stopped markers and missing enabled markers to be repaired. A real failed stop retains its stop intent and must be completed before starting. Process records contain both PID and start time and are checked against the live process. The application PID file is repaired only after startup has been confirmed. Stop receipts belong to one process lifetime; empty or old receipts cannot bypass the business stop command. If both lifecycle copies are corrupt, belong to another directory, or process identity cannot be verified, scripts retain state and fail. Restore the record or controller and retry; scripts do not guess a backend or terminate unrelated processes.

Native processes generate a unit from tools/script/common/atsf4g@.service beside run.sh in their instance state directory. ~/.config/systemd/user/ holds only registration and enablement links to that unit; no instance registry is created in the user's state directory. %Y resolves the unit's actual directory in the package. Systemd, Quadlet and Supervisor identifiers combine the full service name with the first 16 hexadecimal digits of the SHA-256 of the absolute deployment root. The suffix depends only on that directory, excluding startup arguments, execution directory, state directory and package version. Scripts retain the logical deployment path instead of resolving links to version directories. Updating packages through the same deployment entry preserves the name; stop the old instance before switching that entry. Full service names must be unique within a deployment; separate deployments may reuse names. Existing lifecycles stop using their recorded names and adopt the new rule on their next start. Arguments retain their original argv boundaries. The server runs in the foreground and systemd tracks the actual process. Generated scripts use --atapp-foreground for their internal foreground mode. Startup also records the generated stop script for that instance. Normal stop removes startup intent, runs the application's stop command through that script, and waits for the business process to exit before manager cleanup. Stop arguments such as --upgrade retain their argv boundaries. A failed stop command returns failure and leaves the process running; retry stop after resolving the cause, or explicitly use kill. Kill bypasses the business stop command and forcibly terminates the process. Systemd's ExecStop uses the same callback. Supervisor signals a foreground adapter, which calls the stop script without forwarding that signal to the business process. A successful callback runs once per process lifetime and is reset after a crash restart. Direct systemctl/supervisorctl stops also invoke it; timeout termination follows the manager's configuration. Start registers the unit, runs enable --no-reload, then daemon-reload and start under one user-wide lock. Concurrent instance starts follow this order, and unchanged registration links are retained. Stop/kill remove startup intent, disable the instance and stop it through systemctl. Restart=on-failure handles crashes; enable/disable controls startup with the user manager. Disabling a native linked unit also removes its registration. When stopping a live instance, the script restores that registration until both the business stop command and systemctl stop complete, then removes it. This prevents Unit not loaded if the process exits and the manager unloads the unit. The WantedBy startup links stay disabled; a missing package fragment can be rebuilt from the shipped template. After confirming shutdown, stop/kill clear the unit's failed record. If an older test still appears as not-found/failed after its configuration was deleted, run systemctl --user reset-failed <unit> for that confirmed stopped unit. Journal logs remain available. Running after logout or starting at boot may require user lingering, which operators configure separately.

Supervisor uses a private user daemon, Unix socket and program configurations, by default under <package>/var/service-manager/supervisor. Set ATF_SUPERVISOR_DIR before starting to select another absolute directory without newlines, backslashes or semicolons. The directory must be exclusive to the current user. Local builds that link tools to the source tree still write the default configuration into the published package. When that path exceeds the Unix socket length limit, only the control socket uses the user runtime directory; configuration, logs and PID files stay in the package. Stop removes the program configuration and updates the daemon so restarting the daemon does not revive stopped instances. Programs use autorestart=unexpected; exit code 0 does not trigger restart. Ordinary process mode has no crash restart. Logs go to the systemd journal, the Supervisor directory, or output.log in the instance state directory.

Existing Container Images​

The host supervises an existing image; the application image does not need Supervisor installed. Its main process must stay in the foreground. An optional second -- introduces container command arguments; omit it to retain the image's ENTRYPOINT/CMD.

export ATF_SERVICE_MANAGER=supervisord
bash tools/script/service-manager.sh start "$PWD/runtime/game-1" game-1 "$PWD" \
  --container docker registry.example/game:version -- \
  --publish 127.0.0.1:7001:7001 --volume "$PWD/config:/app/config:ro"
bash tools/script/service-manager.sh stop "$PWD/runtime/game-1"

# Optional: override the image's CMD.
bash tools/script/service-manager.sh start "$PWD/runtime/redis-1" redis-1 "$PWD" \
  --container podman docker.io/library/redis:7.2.16 -- \
  --publish 127.0.0.1:16379:6379 -- redis-server --appendonly yes
bash tools/script/service-manager.sh kill "$PWD/runtime/redis-1"

The controller owns container name, detach, restart, rm, cidfile, sdnotify and other lifecycle options; do not override them. Docker/Supervisor use a foreground container client. Stop/kill also use the recorded engine to stop the actual container and verify its exit. Bind mounts, named volumes and images survive stop/kill; do not use the container's temporary layer or anonymous volumes for persistent data. Redis's explicit cleanup command retains its existing image-removal behavior.

Podman with systemd uses rootless Quadlet: the per-instance .container and enablement drop-in stay in the instance state directory. ~/.config/containers/systemd/ holds only links to the file and drop-in directory, respecting XDG_CONFIG_HOME, and Podman's generator produces the unit. Common publish, volume, env and network options become Quadlet fields. Remaining engine options use PodmanArgs and must be compatible with Quadlet's lifecycle settings. This requires a Quadlet-capable Podman and cgroup v2. On environments such as WSL where the system network-online.target is not activated, set ATF_QUADLET_WAIT_NETWORK=0 before starting when the image is cached and the service only needs local networking. The default retains Quadlet's network readiness dependency. Generated units cannot be enabled/disabled directly with systemctl. Start therefore installs an [Install] drop-in with WantedBy=default.target; stop/kill remove it and reload the user manager. Process control still uses systemctl --user. After a successful stop the installed Quadlet link is removed; instance state remains for reuse.

References: systemd service, Supervisor configuration, Podman Quadlet.

Older atsf4g images run the server in the background and the configuration watcher in the foreground through /entrypoint.sh start. For these images, mount tools/script/container-entrypoint.sh read-only at /atf-entrypoint.sh, set --entrypoint /bin/bash, and use -- /atf-entrypoint.sh start as the container command, retaining the original environment and configuration mounts. This compatibility entrypoint reuses the image's configuration initialization, reload and stop behavior. It calls health_check and exits with failure if the server dies, allowing the host supervisor to restart the container. Startup waits up to 180 seconds by default; adjust with the container environment variable ATF_CONTAINER_START_TIMEOUT. No image rebuild is required. Supervising only the foreground container client cannot detect a server exit hidden by the old entrypoint.

Packaging and resetting runtime state​

All three pack_publish.sh archives exclude instance state, PID/CID files, startup errors, control sockets, private Supervisor configuration and reset backups. OpenObserve local passwords, generated values, and data are excluded as a whole. Managed etcd/Redis/OpenObserve work directories inside the deployment are detected even with custom names; their configuration and data remain. Packing reads state without stopping services or clearing the source deployment. A regenerated package can initialize its own state in another deployment directory.

For an older package containing copied runtime state, run as the deployment user on Linux:

# Preview the paths without clearing them.
bash tools/script/reset-service-state.sh
# Back up and clear stale or copied state in this deployment.
bash tools/script/reset-service-state.sh --force
# Explicitly select the deployment when running elsewhere.
bash /path/to/publish/tools/script/reset-service-state.sh -d /path/to/publish --force

The script does not require valid lifecycle records or execute controllers named in copied metadata. Live processes, pending systemd jobs and running containers cause cleanup to fail until normal stop completes. A private Supervisor daemon is shut down only after confirming that none of its programs are active. Only instance registration links targeting this deployment are removed, followed by a systemd reload; other deployments retain their links. Backups are stored under var/service-manager/reset-backups/<timestamp>-<PID>/. Configuration, binaries, OpenObserve passwords, and other dependency data are retained. Dependency work directories and ATF_SUPERVISOR_DIR outside the deployment require separate cleanup.

Deployment Modes​

ModeInputs and outputs
Kubernetesinstall/cloud-native/charts/ and values generate workloads, networking, storage, and logging configuration
DockerDockerfile and entrypoint under install/cloud-native/images/server/
Bare metal/localProcess layout in non_cloud_native/deploy.yaml and sh/ps1 instance scripts

Routine adjustments use values. For new instances, fill proc_desc with the chart name, instance count, starting id, and startup group. Service-side HPA configuration is generated with each instance. Kubernetes HPA and metrics adapters require separate configuration; see HPA integration.

Customization and Design​

The built atdtool lives under <BUILD_DIR>/publish/tools/atdtool/; use atdtool.exe on Windows. Follow local scripts' comma-separated values directory syntax:

atdtool template install/cloud-native/charts -o <OUTPUT_DIR> \
  --values install/cloud-native/values/default,install/cloud-native/values/dev \
  --set global.world_id=1

Charts control instance generation and deployment modes. Templates and shared fragments live under install/cloud-native/charts/libapp/. For observability, see telemetry.
